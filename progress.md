# Progress

This project is a local MVP resume evaluator. It accepts a PDF or DOCX resume, extracts plain text, produces a deterministic 0-100 score, and optionally adds a Gemini-based supplemental score when `GEMINI_API_KEY` is available.

The deterministic core is complete. `backend/extract.py` handles PDF and DOCX extraction, normalizes bullets, and raises clear errors for unsupported or image-only files. `backend/scorer.py` scores resumes across field relevance, structure, parseability, and quantified impact using `backend/field_corpora.json` as the role-specific keyword corpus. The core scorer is intentionally deterministic: the same resume text and field always produce the same result.

The backend API is complete for MVP. `backend/main.py` exposes `/health`, `/fields`, and `/evaluate` through FastAPI. `/evaluate` validates the requested field, accepts only `.pdf` and `.docx`, rejects uploads over 5 MB, applies a basic in-memory per-IP rate limit, writes the upload to a temporary file, runs the pipeline, and cleans up the temporary file afterward.

The Gemini supplement is optional and fallback-safe. `backend/llm.py` skips LLM scoring when text is too short, no parseable sections are detected, prompt-injection patterns are present, or `GEMINI_API_KEY` is missing. When the key is set, it masks basic PII before calling Gemini, validates the JSON shape, retries once on malformed output, and returns a non-fatal status string if the API fails.

The first frontend MVP was built in `frontend/` as a Vite React app with a dark single-column interface, field selection from the backend, PDF/DOCX upload, loading and error states, heuristic score display, collapsible category breakdowns, and a separate Gemini Supplement panel. That initial visual treatment was later superseded by the workstation redesign described below; its fallback behavior remains unchanged, so Gemini failures never hide deterministic results.

The regression suite covers the scoring engine, extraction behavior, pipeline shape, API routing, upload limits, rate limiting, and mocked LLM guardrails. Backend tests run from the project root with `python -m pytest backend -v`; frontend validation runs with `npm run lint` and `npm run build` from `frontend/`.

All items in `suggestions.md` are explicitly marked either addressed or deferred with a reason.

MVP2 adds an optional, separate job-fit evaluation without changing the original four-category resume score. `backend/jd_parser.py` identifies required and preferred JD sections and segments bullet, line-based, or dense-prose requirements. `backend/requirement_extractor.py` resolves each detected term to the existing field corpus and expands multi-skill lines into independent canonical requirements.

`backend/requirement_matcher.py` locates explicit resume aliases and binds nearby years or seniority evidence to one nearest skill within the same clause. This prevents evidence from leaking across adjacent skills or bullets. The first scoring version applied a fixed 0.5 presence baseline and 70/30 required/preferred weighting; later evidence-match calibration, described below, superseded those rules. Empty or vocabulary-free job descriptions return no fabricated score.

`backend/job_fit_llm.py` is a fallback-safe qualitative supplement. It reuses the existing prompt-injection and PII guardrails, validates a strict JSON schema, retries malformed output once, and never changes the deterministic job-fit score. `backend.pipeline.evaluate_job_fit()` and the optional `/evaluate` form field `jd_text` expose the feature additively; calls without a JD retain the MVP1 response shape.

The repository was then separated into independent `backend/` and `frontend/` roots. The backend is now an importable Python package with package-relative imports and module-relative corpus/fixture paths, so it runs reliably from the repository root as `uvicorn backend.main:app`. The frontend API origin is configurable through `VITE_API_BASE_URL`, removing hard-coded coupling while retaining the local default.

Both Gemini integrations were migrated from the deprecated `google-generativeai` package to the supported `google-genai` client API. The resume and job-fit LLM paths now construct `genai.Client`, call `client.models.generate_content`, and use typed `GenerateContentConfig` settings while preserving their existing validation, retry, and fallback behavior.

The frontend now exposes the complete MVP2 workflow rather than only the MVP1 response. Users can enable or disable job-fit analysis, paste a JD, and submit it as `jd_text` with the existing resume upload. The results retain the general resume-quality score and add a distinct job-fit score, required/preferred match counts, priority gaps, expandable per-requirement evidence, years and seniority comparisons, and the optional Gemini job-fit assessment, gap explanations, and phrasing suggestions.

The integrated flow was verified with the complete backend suite, frontend lint and production build, desktop and mobile browser checks with zero horizontal overflow, mode-toggle interaction checks, and a live localhost multipart request using the sample PDF and JD. The live response included all MVP1 and MVP2 keys with three required and two preferred requirements parsed successfully; Gemini was correctly skipped when no API key was set.

The next product pass removed the need to locate or paste a job description for the common path. `backend/job_description_presets.json` now contains five general mid-level profiles: AI / Machine Learning Engineer, Computer Scientist, Software Engineer, Data Scientist, and Cybersecurity Analyst. Their duties and qualifications are paraphrased from stable occupation-level references maintained by O*NET, BLS, and NIST rather than transient employer advertisements. Every preset carries direct source metadata so the API and UI make its provenance inspectable.

The deterministic corpora were expanded with matching `artificial_intelligence`, `computer_science`, `software_engineer`, and `cybersecurity` vocabularies, while the existing `data_scientist` corpus was strengthened. Preset loading validates unique IDs and valid field mappings at backend startup. `GET /job-presets` exposes the catalog, and regression tests confirm every profile has trusted HTTPS sources, parses into required and preferred requirements, produces no fabricated score on empty resume evidence, and scores deterministically.

The frontend is now preset-first. It fetches the field and profile catalogs together, defaults to AI / Machine Learning Engineer, automatically binds the selected profile to its scoring field, and submits the checked-in description as `jd_text`. Users can inspect the profile text and its source links before evaluation. A separate custom mode preserves analysis of real employer postings, and resume-only mode remains unchanged. Results label the selected profile directly while retaining the original resume-quality and Gemini panels.

This preset pass was verified with all 65 backend tests, frontend lint, and a production build. Live localhost checks confirmed five profiles from `/job-presets`, a complete multipart Software Engineer evaluation with 14 required and 9 preferred requirements, correct missing-key Gemini fallback, automatic field changes in the browser, editable custom mode, two visible source links on multi-source profiles, and no horizontal overflow at a 390 px mobile viewport.

An adversarial review of the AI/ML profile then exposed two calibration flaws. `model_validation` appeared in multiple requirement units, and the broad profile expanded alternatives such as NLP, computer vision, generative AI, cloud platforms, Docker, and Kubernetes into cumulative rows. More fundamentally, the 0.5 presence baseline meant a profile with no explicit years or seniority could never score above 50 even when every capability was evidenced.

The extractor now deduplicates each canonical requirement across the complete JD, retaining required placement and the strictest explicit years or seniority qualifier. Unqualified presence receives full credit; the partial 0.5 baseline is reserved for a skill whose stated years or seniority are not evidenced. Aggregate weighting is now 80% required and 20% preferred.

The AI corpus was consolidated into capability groups. The preset currently produces seven core rows and four preferred rows: examples within model evaluation, data engineering, model delivery, applied AI specialization, and production infrastructure each satisfy their group instead of multiplying the denominator. A complete AI preset match now scores 100. The frontend labels the result as a resume evidence match and calls absent terms evidence gaps, making clear that it evaluates what the resume demonstrates rather than asserting the candidate lacks unlisted experience.

The recalibrated engine was verified with all 69 backend tests, including regressions for duplicate merging, stricter qualifier retention, unqualified full credit, the 80/20 aggregate, and the exact AI capability-group shape. Frontend lint and the production build also pass.

The frontend then received its final MVP2 visual pass, based on a clean old-computer workstation rather than a generic web dashboard. The app is now a bounded off-white console with hard rules, graph-paper work surfaces, cobalt operational accents, serif display headings, and monospace controls. Input mode uses a two-pane layout: target, profile, custom-JD, upload, error, and loading controls stay in the left evaluation panel while the right side previews the selected role brief, full checked-in description, and source register. Resume-only mode and custom descriptions retain dedicated preview states.

Completed runs keep a compact source-and-score index in the left panel and divide the right analysis surface into Overview, Evidence, and Guidance tabs. The original deterministic category details, MVP2 requirement evidence, gap labels, years and seniority comparisons, both Gemini fallback statuses, and reset flow are all preserved. The layout collapses to one column below 900 px and simplifies controls below 600 px without horizontal overflow. Browser checks at 1440 x 900 and a 390 px mobile target confirmed the preset preview, custom-description live preview, automatic preset-to-field binding, and zero horizontal overflow. Frontend lint and the production build pass after the redesign.

The Evidence tab was then refined into a document-comparison workspace. A compact status strip reports extracted requirements, matched requirements, and the weighted match rate. Every deterministic requirement now occupies one aligned pair: the original JD wording on the left and the strongest resume evidence on the right, with required/preferred classification, match state, qualifier evidence, and missing evidence kept visible. Exact matched aliases are returned by `backend/requirement_matcher.py`, allowing the frontend to highlight the wording actually found in the resume even when it differs from the canonical capability name. On mobile, each pair stacks as an explicitly labeled job-requirement/resume-evidence unit. All 69 backend tests, frontend lint, and the production build pass after this refinement.

The visual system was then converted from an off-white workstation to a dark console theme. Near-black green-tinted surfaces and subdued phosphor text now cover the full application, including inputs, document previews, result sheets, evidence rows, and responsive states. Borders and grid lines remain deliberately low contrast, matched evidence uses a muted green highlight instead of neon yellow, and amber or red appears only where score and gap semantics require it. The theme retains the existing information hierarchy without glow effects or harsh full-bright green. Frontend lint and the production build pass after the palette change.
